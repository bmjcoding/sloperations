# An agent-first review service for Bitbucket Data Center, EKS, and Bedrock

Research and design date: 2026-11-05. This reference design uses Bitbucket Data Center for source control and webhooks, Amazon EKS for the review runtime, and Amazon Bedrock for model inference. Each adopting team selects its languages, Bitbucket version, models and Regions, then validates the design against its traffic and security requirements.

## Recommendation

Build a policy-controlled review engine with a local CLI and a commit-bound result API. Keep the server reviewer read-only with respect to source code. Let the developer's existing coding agent consume structured findings, make narrowly authorized changes, and push. A small coordinator owns an explicit remediation episode with persistent budgets and termination rules.

Prioritize (1) compiler/type/lint/security invariants, (2) tests and contract checks, (3) a bounded semantic review, (4) verification of actionable findings. Separate **analysis depth**, **reporting sensitivity**, **merge enforcement**, and **permission to remediate**. A single strictness slider cannot safely represent all four.

Fast, exhaustive, deterministic semantic review is not achievable as an unconditional guarantee. Make orchestration, policy, provenance, budgeting, and rule execution reproducible; measure model variance and missed bugs. Never label a timeout, truncated diff, or unreviewed partition clean.

Commercial products already support local agents and bounded loops: see [platform research](platforms.md). The useful differentiation is evidence, low latency, cost/scope enforcement, and enterprise deployment across many repositories.

## 2. Logical architecture

```text
Developer coding agent ── local review CLI ── shared rules/policy
          │                                      │
          ├─ push ── Bitbucket Data Center        │
          │               │ signed webhook       │
          │               ▼                      │
          │       webhook intake on EKS          │
          │               ▼                      │
          │       durable queue + PR coordinator ◄┘
          │               │ snapshot + policy + reserved budget
          │               ▼
          │       warm review workers
          │       ├─ deterministic analyzers
          │       ├─ bounded context selection → Bedrock
          │       └─ candidate verification
          │               ▼
          │       immutable manifest + finding ledger
          │               ├─ commit status / Code Insights
          │               └─ authenticated agent API
          └──── wait / claim finding batch / fix / validate / push
```

Choose the smallest stateful service decomposition that meets the team’s requirements. No need for an autonomous planning framework, agent mesh, vector database, or graph database in the first version. Start with repository mirrors, symbol indexes, durable state, encrypted artifacts, and a bounded task runner. Add cross-repository retrieval only for named dependency contracts that demonstrably improve evaluations.

### Webhook intake and durable work

Verify the signature against raw bytes, validate project/repository allowlists, normalize the event, durably enqueue, then acknowledge quickly. Do not run review synchronously in the webhook handler. Deploy a webhook intake endpoint on EKS, or reuse a compatible endpoint if the team already operates one. Bitbucket documents HMAC signing and event identity headers. [Webhook security](https://confluence.atlassian.com/bitbucketserver094/manage-webhooks-1489802210.html), [Data Center event payloads](https://confluence.atlassian.com/bitbucketserver104/event-payload-1822591266.html).

Suggested events: PR opened, source updated, reopened where supported, retargeting/metadata changes that affect review, and merge/decline/delete for cancellation. Also account for destination-branch changes: source SHA alone cannot describe integration correctness. Map precise event names to the installed Data Center version. Keep reviewer status and comment updates out of the trigger set.

A Standard SQS queue plus conditional durable state is sufficient initially; FIFO grouping by PR may reduce disorder, but it does not remove application idempotency. Queue delivery and remote API side effects must be treated as retryable and potentially duplicated. [SQS visibility documentation](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html).

### Coordinator invariants

- Run identity: host/repo ID, PR ID, source SHA, destination SHA, review-base/merge-base SHA, policy hash, analyzer versions, model snapshot/config, context-manifest hash, prompt version, schema version.
- Delivery identity is distinct from semantic run identity. Repeated webhook delivery or push+PR event overlap must not buy another model review.
- Use conditional leases with fencing tokens. A stale worker cannot finalize after its lease expires or a newer generation supersedes it.
- Coalesce bursts with a short configurable debounce (initially around 1 second); cancel obsolete queued/running work at each expensive boundary. Cancellation may not stop already billed inference.
- Re-read PR state before dispatch and publication. Results always name immutable SHAs. Consumers and merge gates must independently reject stale results; a check immediately before publication cannot make the subsequent Bitbucket update atomic.
- Persist result + publication intent transactionally; an outbox retries status/report publication without rerunning inference. Acknowledge queue work only after durable state is safe.
- Retargeting or changed policy can invalidate a result even without a source change. Never reuse a result solely because the head SHA matches.

## 3. Review computation

### Snapshot and diff correctness

Maintain read-only local mirrors or content-addressed object caches. Fetch pinned objects, not a moving branch; verify requested SHAs are present. Use per-job isolated snapshots so parallel PRs cannot mutate shared working files. Handle renames, deletions, mode changes, LFS pointers, submodules, symlinks, binaries, generated content, and API pagination explicitly.

Record both PR-introduced changes (merge-base to head) and target integration effects. Data Center may render an effective/preview-merge diff, so do not assume local merge-base line numbers match the UI. Keep analysis coordinates and display coordinates distinct. [Atlassian's explanation](https://developer.atlassian.com/server/bitbucket/how-tos/code-insights/).

Large or incomplete API diffs require git-object retrieval or an explicit partial result. Do not silently sample an oversized PR and report success. Analyze configurations, dependency manifests/lockfiles, API schemas, migrations, and build scripts with appropriate rule packs; file extension is insufficient for routing risk.

### Deterministic analysis first

Run pinned versions of the relevant format/lint/type/static-security/secret/architecture tools. Reuse existing CI outputs when their commit, policy/tool versions, environment and coverage match. Do not pay a model to rediscover syntax errors or invent complexity counts. Select analyzers after languages are known; possible components include compiler tooling, ESLint/Ruff, SpotBugs/Error Prone, Semgrep/approved equivalent, dependency scanning, IaC policy, and secret detection. Licenses and enterprise features require separate review before embedding or redistribution.

Use diff-aware findings against a known baseline, but do not equate changed lines with causal impact. Changing a helper, authorization wrapper, interface, dependency, or configuration can break untouched consumers. Re-run affected dependent checks and retrieve relevant callers. Semgrep documents [diff-aware CI setup](https://semgrep.dev/docs/semgrep-ci/sample-ci-configs); Sonar distinguishes overall and new-code metrics in its [metric definitions](https://docs.sonarsource.com/sonarqube-server/2026.1/user-guide/code-metrics/metrics-definition).

### Context selection

For each changed symbol include its before/after body, containing imports/types, direct callees/callers, nearest behavior tests, relevant API/schema contracts, and effective path policy. Add targeted data-flow context for auth, resource lifetimes, transactions, retries, concurrency, and serialization. Prioritize exact symbol resolution and lexical references before embeddings. Pin retrieval to a snapshot and stable ordering.

Use a bounded dependency frontier, with explicit exclusions and context limits. A cheap model reporting no issue does not prove broader review is unnecessary; risk routing should use deterministic signals and mandatory category rules. Low-risk sampling in evaluation should look for systematic misses caused by routing.

On re-push review the delta since the last reviewed head plus invalidated dependencies and unresolved findings. Keep a complete current-head coverage manifest assembled from reusable and new results. Any change to base, dependency blobs, rules, prompts, model, or context selection can invalidate prior findings/clean partitions. This prevents the incremental optimization from turning into cumulative blind spots.

### Bounded semantic pass

Default to one model pass per bounded module group, with a small parallelism cap. Ask for concrete failure conditions, affected behavior, source evidence and a validation recipe; permit an empty finding list. Do not require a quota of comments or numerical code-quality scores. A small model is not automatically cheaper if it requires retries or misses expensive defects: select using replay evidence.

Treat candidates as hypotheses. Validate file existence, SHA, ranges, cited snippets and changed-code causality in code. Use targeted tests or static checks where available. A second independent model can challenge important ambiguous candidates within a fixed budget, but agreement is not proof. Never let an LLM suppress a verified compiler/security finding without an authorized exception.

Represent missing context as uncertainty or incomplete coverage. Severity is impact; confidence is strength of evidence; remediation permission is a separate decision. Self-reported model confidence is not a calibrated probability. Initially auto-remediate only evidence-backed rule violations or findings with reliable validation and reversible scope.

### Performance review is its own dimension

Distinguish an evidence-backed regression (for example a new query in a bounded loop with query-count proof) from a possible optimization. Require workloads, before/after results, repeat counts, variance and environment for performance gating. Default suggestions about allocation, caching or algorithm replacement to advisory until validated. Tests and benchmark subprocesses receive explicit CPU, memory and duration limits.

Complexity and duplication are deterministic signals, not correctness proofs. Compare changed functions against a baseline; distinguish cyclomatic from cognitive complexity, and exact/token clone detection from semantic redundancy. Never force unrelated old complexity to be fixed on a routine PR. Avoid a repo-wide percentage that a monorepo can dilute. Exceptions for generated code and tests need documented policy rather than arbitrary suppressions.

## 4. Latency and Bedrock constraints

**Proposed targets, not observed results:** define a small warm PR class (at most 10 changed source files, 500 changed lines, supported language, no dependency/schema migration, bounded context). For this class target deterministic first results within 2–5 seconds and standard semantic completion at p50 ≤15 seconds / p95 ≤30 seconds. Measure queue wait, fetch, tool time, context build, inference and publication separately. Cold repositories, long builds, unavailable model quota and large PRs need separate SLO classes and truthful partial/pending states.

| Work mode | Proposed budget/target | Intended use |
|---|---|---|
| Local deterministic | incremental, often subsecond to a few seconds; benchmark by language | fast feedback while coding |
| Fast PR | ≤30-second wall deadline for supported small warm PRs | default bugs/security + bounded semantic pass |
| Standard PR | ≤60-second deadline, bounded extra context/verification | broader correctness and contracts |
| Deep PR | ≤180-second deadline or separate async check | high-risk migrations, auth, concurrency, integration |

A deadline is a resource ceiling, not a guarantee of a completed clean review. Mandatory unfinished checks keep the merge gate non-successful.

Keep warm worker Deployments and git/index caches; scale from queue age with baseline capacity. A Kubernetes Job per tiny review can put image pull/scheduling ahead of analysis, so reserve separate isolated Jobs for executing repository code. Partition work with bounded concurrency instead of one request per file. Keep output concise; output-token generation often sets the tail. Full tests, browser sessions and mutation testing belong in a separate tier when they exceed the PR fast-path budget.

Bedrock supports provider/model-specific prompt caching; stable prefixes help but cache hits are not guaranteed and cache writes can cost more than ordinary inputs. Measure read/write token counters. Keep dynamic PR text at the end and caches scoped to authorized data. [Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html).

Bedrock's structured-output docs specify a supported JSON Schema subset, per-model/API support, first-schema compilation up to approximately 90 seconds, and grammar caching for 24 hours. Use one small stable candidate schema and prewarm outside request handling; confirm deployed behavior. Token truncation can still produce incomplete output. Validate semantics and bounds yourself. Do not build dynamic per-repo enums into the schema and trigger fresh compilation. [Structured outputs](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html).

Use a provider adapter around approved Bedrock APIs, deadlines, usage metering, quota handling and structured decoding. Pin model version where available and record exact endpoint/inference profile, model ID, Region, sampling and reasoning controls. Do not silently fail over to another model or Region. Confirm permitted Regions and routes with the team responsible for data handling before enabling inference. Queue or return incomplete when limits are reached. Model tokens-per-minute, requests-per-minute and concurrent calls need org/project fairness controls, not only more EKS pods.

## 5. Determinism that can actually be provided

1. Pinned rules, tool images, file snapshots, traversal/order, locale and build dependencies make rule execution reproducible within defined environmental limits.
2. Freeze prompt/template/schema/model/config and deterministic context packing. Use supported low-variance sampling; temperature zero is not proof of determinism and some models do not support it.
3. Cache exact completed semantic results by the full run/context identity. The same key replays the stored result without buying a new stochastic sample. Cache reuse must respect authorization and retention.
4. Canonicalize candidates, stable-sort, deduplicate and assign stable fingerprints in service code, never from model prose alone.
5. Gate from evidence and policy. Keep a ledger of finding transitions so a repeated head cannot acquire different findings just because a model was called again.
6. Measure repeated fresh-run finding-set overlap and gate-decision disagreement on a frozen evaluation corpus. Replay determinism is distinct from new-inference repeatability.

Tests can be flaky and static tools can have false positives. Preserve provenance, distinguish flaky/infrastructure failures, and do not turn deterministic tool output into an unsupported correctness guarantee.

## 6. Agent-consumable protocol

Expose authenticated endpoints such as:

```text
GET  /v1/repositories/{id}/pull-requests/{pr}/reviews?head={sha}
GET  /v1/reviews/{run}/findings
GET  /v1/reviews/{run}/events?after={cursor}   # resumable long-poll or SSE
POST /v1/episodes/{episode}/claims           # atomic exclusive batch lease
POST /v1/episodes/{episode}/attempts         # push + evidence acknowledgement
```

These are proposed internal endpoints, not Bitbucket endpoints. Bind every request to user/service identity and repository authorization. The CLI initiates outbound connections through a network route approved for the deployment. The daemon/CLI waits deterministically; invoke the coding model only when actionable work exists. Reconnect by cursor, with jitter/backoff, and enforce claim expiry/fencing. Persist progress so restarting a coding agent does not reset budgets or replay fixes.

A review envelope should include schema version, immutable run ID, repo/PR identity, source/destination/base SHAs, effective policy hash, state, coverage, evaluated/skipped categories, tool/model provenance, cost usage and finding IDs. Service code creates trusted envelope metadata; model output is only the candidate payload.

Each finding needs stable ID and rule/category, severity, evidence class, introduced/pre-existing/uncertain classification, file/blob/symbol/range, trigger and failure mechanism, related evidence, allowed remediation scope, validation recipe IDs, disposition, and replacement/supersession history. Avoid free-form shell execution instructions: recipes reference allowlisted commands in a trusted bundle. Patches are optional proposals and must match their source blob before application.

Make a SARIF export for integration with existing analysis tooling, but keep remediation leases, episodes and budgets in your own protocol. A SARIF message alone does not coordinate agents.

## 7. Preventing endless review/fix loops

A prompt that says “stop after two tries” is insufficient. The coordinator must own limits outside either model.

### Proposed episode limits

- An episode begins with a reviewed snapshot and frozen finding batch, allowed paths/symbols, accepted behavior, policy version and cumulative resource budget.
- Default maximum **two automatic repair pushes**, plus an aggregate wall-clock deadline (initially 10 minutes). Values are starting policy choices for pilot measurement, not vendor defaults.
- Persistent per-finding attempts and episode-wide model/tool/token/USD limits include local fixer calls where the gateway can meter them. Without a metered local integration the server can enforce its own spend and accepted pushes, but cannot guarantee a cap on the laptop agent's API bill.
- Fixer cannot silently create a new episode by pushing, closing/reopening, restarting, force-pushing, changing its identity or altering commit metadata. Reset needs an authenticated authorized action with audit.
- One active fixer lease per PR (or provably disjoint batch); use fencing and expected source SHA. Non-fast-forward/changed-head updates require re-evaluation, never an automatic force push.
- Every repair push receives deterministic affected checks, original finding verification and bounded regression screening. Catch serious newly introduced bugs; do not broaden the goal into new optional improvements.
- New low-severity or unrelated findings go to a separate advisory/backlog channel. A new severe regression can block and trigger escalation, but cannot mint another automatic repair budget.
- Repeated normalized patch, recurring fingerprints, oscillation, scope expansion or no independently verified progress stops automatic remediation. Finding disappearance alone is not verified progress.
- Time/cost/attempt exhaustion ends as NEEDS_ATTENTION, never PASS. Cancellation releases leases and prevents any additional dispatch; already-started model requests may still cost money.

A reviewer has no source push credentials. A fixer cannot modify policy, suppressions, build requirements, baseline definitions, generated evidence, or remove/weaken tests to clear a finding. Dependencies and public API/schema changes require explicit scope permission. Check the resulting diff and enforce protected paths centrally; prose reminders alone do not enforce scope.

### State machine

```text
QUEUED → SNAPSHOTTED → ANALYZING → VERIFYING → COMPLETE
   └──────────── obsolete head/base ───────────→ SUPERSEDED
   └────────── timeout/tool/context failure ───→ INCOMPLETE

COMPLETE with eligible findings → CLAIMED → FIX_SUBMITTED → REVERIFY
REVERIFY → VERIFIED | NEEDS_ATTENTION | next permitted repair attempt
Any active episode → CANCELLED / BUDGET_EXHAUSTED / SCOPE_VIOLATION
```

Finding states include OPEN, CLAIMED, ATTEMPTED, VERIFIED_FIXED, REJECTED_WITH_REASON, WAIVED_BY_AUTHORIZED_OWNER, PRE_EXISTING, and SUPERSEDED. A fixer's “fixed” assertion is not VERIFIED_FIXED. Only evidence at the new head can make that transition. Source deletion, disabling a rule, or excluding a directory cannot masquerade as resolution.

## 8. Policy hierarchy and tiered nit-pickery

Use central policy → Bitbucket project defaults → repository defaults → ordered path rules. Support future GitHub org/owner and repo adapters over the same logical hierarchy. Read active repo config from the protected target branch; a PR proposing policy changes is reviewed under the prior effective policy. Central mandatory floors cannot be weakened by repo/path settings. Validate schema, canonicalize paths and reject conflicting ambiguous overrides.

Store an explainable effective configuration per path and hash it into the run. Path overrides specify explicit priority and deterministic tie-breaking; normalize case rules, traversal and symlinks. A config compiler should emit a plan so a monorepo owner can see why a path gets a particular depth or budget.

| Category | Baseline default | Opt-in stricter behavior |
|---|---|---|
| Correctness | observable bug/regression candidates; evidence required for automatic fix | wider dependency/context analysis |
| Security | mandatory approved rules + risk-routed semantic checks | stronger verification for sensitive changes |
| Performance | advisory unless measurable regression or approved invariant | query/allocation/latency budgets by path |
| Cyclomatic/cognitive complexity | report regressions on changed functions | path-specific ratchets/limits |
| Duplication/redundancy | new exact/token clones advisory | approved thresholds; semantic duplication advisory |
| Architecture | deterministic import/dependency boundaries enforced | proposed design alternatives separately |
| Style/naming/docs | formatter/linter handles enforceable rules | optional advisory suggestions, tightly capped |

Keep mandatory security/CI requirements independent of budget/depth selection. Users may reduce optional analysis, not erase required checks. Aggregate budgets across path partitions: splitting a PR into many directories cannot multiply its cap. For mixed-risk PRs partition work and apply required checks to each path; use one coherent overall merge decision.

Proposed configuration example is in [review-policy.example.yaml](review-policy.example.yaml). It is a design artifact, not configuration recognized by any existing product.

## 9. Bitbucket Data Center publication

Use one stable commit build-status key for the required gate, and a Code Insights report for rich human inspection. The result API is the canonical agent contract; comments are optional projections, not the work queue. Bitbucket's report API is commit-bound and includes annotations. A failed Code Insights report alone does not block merging; configure required build/merge checks for the installed version and edition. [Code Insights behavior](https://developer.atlassian.com/server/bitbucket/how-tos/code-insights/).

Data Center report resources use `/rest/insights/{version}/projects/{projectKey}/repos/{repositorySlug}/commits/{commitId}/reports/{key}`. Use the deployed version's REST contract, not the older how-to's simplified path. See the [versioned Insights reference](https://developer.atlassian.com/server/bitbucket/rest/v802/api-group-insights/). Common legacy build publication uses `/rest/build-status/1.0/commits/{sha}`; verify with the installed API. Status values are commonly INPROGRESS/SUCCESSFUL/FAILED, but internal review states must remain richer.

Only publish success once every mandatory partition is complete and no blocking finding remains. On partial/tool failure keep non-success status and explain it; optional analysis failures can follow an explicit repo policy. A successful deterministic sub-check must not be presented as overall review completion. Destination changes require revalidation; ordinary source-commit status alone cannot assert that the reviewed source/base pair is still current. Evaluate a version-supported custom merge check or equivalent enforcement if existing build requirements cannot validate both SHAs.

Use idempotent report updates with version-appropriate annotation replacement. Do not assume Data Center deduplicates annotations automatically. Enforce report/annotation limits and link overflow to the canonical manifest. UI annotations may show only changed lines; preserve off-diff causal evidence in the API. Avoid publishing private source/evidence via public report links.

Cloud compatibility, if later needed, requires a separate adapter: Cloud uses workspace/repo identities and `/2.0/repositories/.../commit/.../reports` resources. Do not reuse Data Center payloads. [Cloud reports API](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-reports/).

## 10. Cost and capacity controls

Track total cost per completed reviewed change and per correctly fixed issue, not cost per model call. Include repeated heads, verification, fixes, local runs, cache writes, tool CPU, indexing, storage and operator triage. Compare a cheap pass plus verifier against a stronger single pass using the same held-out corpus.

```text
review_cost = Σ[(uncached_input × input_rate
              + cache_write × write_rate
              + cache_read × read_rate
              + billed_output_and_reasoning × output_rate)/1_000_000]
              + tool_compute + amortized_index_storage
monthly_cost = reviewed_heads × mean_review_cost
               + local_agent_cost + operations
```

Rates depend on approved model, API, inference mode, Region and contract. Avoid quoting vendor seat pricing as your inference cost. Request actual Bedrock/gateway rates before forecasting. For intuition only: at 100,000 reviewed heads/month, average review costs of $0.05/$0.25/$1.00 imply $5k/$25k/$100k in review spend before other costs. These are arithmetic scenarios, not market prices or model estimates.

Reserve a pessimistic maximum charge before every inference/tool dispatch with atomic ledger updates; settle actual usage afterward. Keep pending/cancelled in-flight reservations conservative until billing outcome is known. Budget retries at the same episode/run identity. Disable hidden SDK retries or charge their maximum attempt envelope. Never automatically retry a semantically unproductive run indefinitely. Reserve separate mandatory-check capacity so optional spend exhaustion cannot silently skip required analysis.

Enforce org, project, repo, PR, episode and identity caps. Use fair queues and concurrency/token reservations to prevent a giant monorepo exhausting Bedrock quota for everyone. Circuit-break duplicate storms, provider errors, runaway cost velocity and unexpectedly huge prompts. Budget exhaustion produces visible incomplete analysis or escalation; automatic fallback to a less complete “clean” result is prohibited.

For capacity, Little's Law provides an initial estimate: arrival rate × mean service time ≈ average concurrent work. At 2 PR-head events/second and 20-second mean processing, roughly 40 reviews are active on average before headroom; model-call concurrency and token demand may be the limiting resources. Measure burst percentiles and cancellation waste rather than sizing to this example.

## 11. Enterprise deployment boundaries

For each deployment, define the source data allowed in model requests, permitted Regions and inference routes, and logging and retention limits. Route inference through a Bedrock VPC endpoint or a gateway that meets those requirements. Scope workload identities to the resources each needs. Bedrock offers [PrivateLink connectivity](https://docs.aws.amazon.com/bedrock/latest/userguide/vpc-interface-endpoints.html); EKS [Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html) associates IAM roles with service accounts, but pods sharing a node are not a strong isolation boundary.

Separate webhook intake, source retrieval, analysis, sandbox execution and publication identities. The reviewer can read permitted repositories and publish review results, but has no branch-write/merge permission. Sandboxes executing builds/tests receive no publishing credential, production secret or broad network access. Harden read-only parsing too: malicious paths, archive entries, symlinks and resource exhaustion are possible without executing the build. Restrict Git hooks/config/protocols, avoid arbitrary submodule URLs, and pin approved tool downloads/images.

Treat PR descriptions, comments, repository instructions and source text as untrusted data. They cannot grant tools, elevate permissions, change central policy or supply trusted validation commands. Retrieval must enforce repo ACLs before returning context, including cross-repo indexes. Findings and evidence can contain secrets: redact logs and telemetry, encrypt artifacts, apply approved retention, and authorize manifest downloads. Use synthetic, public, or otherwise authorized code for vendor benchmarks.

Before rollout, validate these boundaries with the adopting team’s security and platform owners. Keep mandatory security checks and human approvals in place unless the responsible owners approve a change.

## 12. Evaluation and rollout

Build a stratified evaluation corpus from authorized repository history containing bug-introducing PRs, clean PRs, pre-existing defects, target-branch interaction bugs and actual accepted/rejected reviewer findings. Split by repository/time to reduce leakage. Seed known mutation classes for the “obvious issue” suite: missing authorization, tenant leakage, null handling, dropped await, incorrect transaction boundary, retry non-idempotency, swallowed exception, accidental API break, timeout removal, N+1 query, migration incompatibility, and unbounded resource use. Include good changes that superficially resemble each bug.

Freeze snapshots and trusted expected behavior. Blindly adjudicate new findings: a finding missing from an answer key is not automatically false, and a fix being accepted is not automatically correct. Use models as assistants, not the sole ground-truth authority. Relevant primary research: [CR-Bench](https://arxiv.org/abs/2603.11078) highlights noisy findings versus resolution; [CRJudgeBench](https://arxiv.org/abs/2609.37216) studies plausible invalid reviews; [SecPRBench](https://arxiv.org/abs/2610.33509) evaluates real bug-introducing security changes. These preprints and benchmarks do not establish performance on the adopting team’s workload.

Measure precision and recall by category/severity and causal correctness; false blocking rate per clean PR; p50/p95/p99 end-to-end latency; incomplete coverage rate; repeat-inference gate disagreement; actual dollars per head/episode; regression-free automatic resolution; scope violations; average/p95 pushes to completion; rate of repeated/oscillating findings; production escapes and reverts. Stable-ID/fingerprint accuracy deserves its own test set.

Before automatic fixes, prove the coordinator survives duplicate/reordered webhooks, force pushes, mid-run destination changes, simultaneous fixers, worker death, lease expiry, provider timeouts/429s, partial JSON, status-publication failure, partial diffs, poisoned repo config, and restart/replay without budget resets. These distributed failure tests are more valuable than a collection of prompt snapshot assertions.

Roll out in stages:

1. Establish immutable snapshots, effective policy, coverage manifests, usage ledger, CI/rule ingestion and status projection in shadow mode.
2. Share a pinned local CLI/rule bundle; compare local and server results on the same snapshot. Local unsigned “passed” claims do not bypass mandatory server checks.
3. Add one bounded semantic pass; evaluate precision/recall and latency before adding a verifier or extra models.
4. Offer machine findings to local agents with explicit claims, two-push ceiling and verified completion. Start with low-risk reproducible defects.
5. Add risk-routed deep analysis, monorepo path inheritance and approved contract retrieval based on measured misses.
6. Promote recurring accepted mistake classes into architecture/types/checks through separate reviewed changes.

A useful pilot release gate is zero bypasses of the budget/scope/staleness invariants in fault tests, demonstrable recall on the seeded obvious-issue suite, and agreed precision/latency thresholds on the held-out evaluation corpus. Do not invent universal thresholds without baseline volumes and error costs.

## 13. Decisions still needed

- Identify the Data Center version, supported webhook events, and how to enforce required checks at merge time.
- Inventory languages, build systems, repository layout, analyzers, and package sources available to the worker sandbox.
- Select permitted Bedrock models, APIs, Regions and inference profiles. Confirm quotas, logging and retention requirements.
- Measure daily and peak PR-head event rates and typical diff sizes. Set a latency percentile target for small PRs.
- Choose supported coding agents and determine whether their inference can be metered.
- Define blocking categories, eligible automatic fixes, and who can waive or reset an episode.
- Choose where to run webhook intake, queueing, metadata storage, and encrypted artifact storage. Reuse compatible services where available.

These determine the implementation plan; they do not prevent building the provider-independent result protocol and fault-tested coordinator first.

## 15. Video follow-up: replay, patch growth and handoff timing

The [timestamped video analysis](video-tfcdwrebafm.md) adds these proposed requirements:

- Provide a deterministic fixture/replay adapter for model responses and event timing so orchestration, recovery and client behavior can be tested without repeated inference charges. Keep a separate live Bedrock evaluation lane for reasoning, actual latency and billing.
- Bound automatic repair by distinct files, changed symbols, final repair diff size and cumulative churn in addition to existing attempt/time/cost/scope caps. Measure growth against the authorized starting head; deletions cannot offset added lines and oscillating/reverted edits still count toward cumulative churn. A tiny original PR cannot create an unreasonable growth allowance through a ratio alone.
- Let an agent propose fix/rejection/intentional-behavior/exception/escalation dispositions with counterevidence and actor identity. Policy decides which dispositions may clear a blocker. An aggregate quality score cannot clear mandatory checks or reset resources.
- Trace result publication, client pickup, claim, patch completion, validation, push and re-verification separately. Improve end-to-end completion time rather than inference duration alone.

The example policy now illustrates absolute patch-growth caps; these are uncalibrated pilot settings, not implemented enforcement or generally appropriate thresholds.
